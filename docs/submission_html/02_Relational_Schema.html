1. Formal ER-to-Relational Mapping Methodology

The conceptual Entity-Relationship design was transformed into a formal relational schema using the standard 4-step mapping algorithm. Our schema contains 22 normalized tables (10 primary entity/audit relations and 12 associative junction tables), spanning 141 typed columns and 31 foreign key constraints.

  1. Step 1: Mapping Regular (Strong) Entities: For each strong entity type (officers, cases, people, organizations, vehicles, devices, locations, evidence), we synthesized a distinct relation containing all atomic attributes. The primary key of each relation is enforced via a single-attribute PRIMARY KEY constraint (e.g. officer_id, case_id, person_id). All non-key attributes that are mandatory are enforced with NOT NULL constraints.
  2. Step 2: Mapping Weak Entities: For existence-dependent weak entities (evidence_custody and case_activity), we synthesized dedicated relations comprising all local discriminator attributes plus the primary key of the identifying parent relation as a foreign key attribute with NOT NULL constraints (e.g. evidence_custody.evidence_id → evidence.evidence_id and case_activity.case_id → cases.case_id).
  3. Step 3: Mapping Binary 1:N Relationships: For each 1:N relationship from entity S (1-side) to entity T (N-side), the primary key of S is included as a foreign key column within relation T. Examples in our schema:
    • Lead Investigator Assignment: cases.lead_officer_id → officers.officer_id (ON DELETE SET NULL, preserving case docket continuity).
    • Case Docket Exhibit Linking: evidence.case_id → cases.case_id (ON DELETE RESTRICT, strictly preventing accidental evidence spoliation).
    • Seizing Officer Attribution: evidence.collected_by_officer_id → officers.officer_id (ON DELETE SET NULL).
    • Custody Custodian Logging: evidence_custody.officer_id → officers.officer_id (ON DELETE RESTRICT, maintaining legal witness integrity).
    • Audit Performer Logging: case_activity.officer_id → officers.officer_id (ON DELETE SET NULL).
  4. Step 4: Mapping Binary M:N Relationships: For each of the 12 many-to-many relationships in our domain model, we synthesized a dedicated associative relation (junction table). The primary key of the junction table is formed as a composite key of the primary keys of the participating entities: {PK(A), PK(B)}. Relationship attributes (e.g. role_in_case, role_in_org, recovery_context) are stored as non-key columns within the junction relation. All 24 foreign keys in the 12 junction tables enforce ON DELETE CASCADE, guaranteeing that orphaned associative linkages are automatically purged.

8. Formal Normalization Proofs (1NF through BCNF)

We systematically evaluated the functional dependencies (FDs) across all 22 relations to verify formal adherence to Boyce-Codd Normal Form (BCNF). Below are the formal proofs for three representative core relations:

8.1 Case Management Relation: cases

  • Attribute Set: R = {case_id, title, description, case_type, status, priority, lead_officer_id, incident_date, created_at, updated_at}.
  • Functional Dependencies:
    FD1: case_id → {title, description, case_type, status, priority, lead_officer_id, incident_date, created_at, updated_at}
  • Candidate Keys: K = {case_id}. Single candidate key.
  • 1NF Verification: All attributes are strictly atomic scalar values; status and priority are atomic enumerated strings; no multivalued or nested sets exist.
  • 2NF Verification: The candidate key is a single attribute (case_id). Therefore, no partial functional dependencies are mathematically possible.
  • 3NF Verification: There are no transitive dependencies X → Y → Z where Y is non-prime. lead_officer_id is a foreign key, but it does not determine any other column in cases (officer name, badge, and department reside solely in officers).
  • BCNF Verification: For every non-trivial functional dependency X → Y, the determinant X is a superkey (specifically, case_id). Therefore, cases is in strict BCNF.

8.2 Forensic Exhibit Relation: evidence

  • Attribute Set: R = {evidence_id, case_id, evidence_number, item_type, description, storage_location, custody_status, collected_date, collected_by_officer_id, created_at, updated_at}.
  • Functional Dependencies:
    FD1: evidence_id → {case_id, evidence_number, item_type, description, storage_location, custody_status, collected_date, collected_by_officer_id, created_at, updated_at}
    FD2: evidence_number → {evidence_id, case_id, item_type, description, storage_location, custody_status, collected_date, collected_by_officer_id, created_at, updated_at}
  • Candidate Keys: K1 = {evidence_id}, K2 = {evidence_number} (enforced via UNIQUE).
  • 1NF, 2NF & 3NF: Single-attribute keys preclude partial dependencies. Transitive officer and case details are deliberately omitted, eliminating transitive dependencies.
  • BCNF Verification: Both determinants (evidence_id and evidence_number) are candidate keys (superkeys). Thus, every non-trivial FD has a superkey determinant. evidence satisfies BCNF.

8.3 Associative Relation: case_people

  • Attribute Set: R = {case_id, person_id, role_in_case, notes, added_at}.
  • Functional Dependencies:
    FD1: {case_id, person_id} → {role_in_case, notes, added_at}
  • Candidate Keys: Composite primary key K = {case_id, person_id}.
  • 2NF Verification: Neither case_id → role_in_case nor person_id → role_in_case holds individually, because an individual may serve as a "Witness" in Case A and a "Subject" in Case B. Non-prime attributes depend on the entire composite key. Full functional dependency holds.
  • 3NF & BCNF Verification: There are no non-key determinants. The only non-trivial FD has the composite candidate key as its determinant. Therefore, case_people satisfies BCNF.

8.4 Architectural Persisted Separation (Polyglot Justification)

Our schema deliberately maintains complete relational normalization in PostgreSQL for all entity states, custody transfers, and audit logs to enforce ACID consistency. Unstructured polymorphic documents (witness statement transcripts, CCTV video metadata, phone forensics dumps) are segregated into MongoDB (investigation_documents) linked via foreign document references (case_id and related_entity_ids). This prevents relational denormalization and guarantees both rigorous transactional integrity and schema flexibility.
