1. ER-to-Relational Mapping Methodology

We transformed our conceptual ER model into a relational database schema by applying the standard 4-step mapping algorithm:

  1. Step 1: Mapping Strong Entities: For each strong entity (officers, cases, people, organizations, vehicles, devices, locations, evidence), we created a relation containing all atomic attributes, with the designated primary key enforced via PRIMARY KEY constraints.
  2. Step 2: Mapping Weak Entities: For weak entities (evidence_custody, case_activity), we created relations including all local discriminator attributes plus the primary key of the owner parent relation as a foreign key with NOT NULL constraints.
  3. Step 3: Mapping 1:N Binary Relationships: For 1:N relationships (e.g. Lead Officer on Cases, Case on Evidence), the primary key of the "1-side" entity is placed as a foreign key column in the "N-side" relation (e.g. cases.lead_officer_id referencing officers.officer_id).
  4. Step 4: Mapping M:N Binary Relationships: For each of the 12 many-to-many relationships, we created a distinct associative relation whose composite primary key is formed by the primary keys of the participating entities, augmented by relationship-specific descriptive columns.

3. Normalization Analysis & Formal Proofs (1NF to BCNF)

We systematically evaluated the functional dependencies (FDs) of our relations to ensure strict adherence to Boyce-Codd Normal Form (BCNF).

3.1 First Normal Form (1NF) Compliance

A relation is in 1NF if and only if all domain values are atomic and there are no repeating groups.

  • Violation Avoidance: Rather than storing aliases or phone numbers as multivalued arrays or comma-delimited strings within people, distinct phone numbers and address lines are maintained in dedicated columns, and person-to-asset linkages are isolated in 1NF associative relations.
  • Atomicity: Coordinates in locations are stored as separate atomic NUMERIC(10,8) latitude and NUMERIC(11,8) longitude values, not combined geometric strings.

3.2 Second Normal Form (2NF) Compliance

A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on the entire primary key (no partial dependencies).

  • Single-Attribute Keys: All 10 entity relations (e.g. cases, officers, people) possess single-attribute primary keys (e.g. case_id). Therefore, partial functional dependencies are mathematically impossible.
  • Composite Key Junctions: In our 12 associative relations (e.g. case_people with composite PK {case_id, person_id}), the non-key attributes are role_in_case, notes, and added_at. These attributes describe the specific relationship between the case and the person:
    {case_id, person_id} → {role_in_case, notes, added_at}
    Neither case_id → role_in_case nor person_id → role_in_case holds individually because a person may be a "Witness" in one case and a "Suspect" in another. Thus, full functional dependency is preserved.

3.3 Third Normal Form (3NF) & BCNF Compliance

A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key. A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a superkey.

Consider relation evidence:

Functional Dependencies for Relation EVIDENCE
FD1: evidence_id → {case_id, title, evidence_type, description, status, storage_location,
                     chain_of_custody_hash, barcode, collected_by_officer_id, created_at, updated_at}
FD2: barcode → {evidence_id, ...}  (Candidate Key via UNIQUE constraint)

In evidence, the only determinants are evidence_id and barcode. Both are candidate keys. We do not store officer names or case titles in evidence (which would introduce transitive dependencies evidence_id → case_id → case_title). Instead, such details are resolved dynamically via relational JOINs.

Therefore, every determinant in the schema is a superkey, and the schema satisfies Boyce-Codd Normal Form (BCNF).
