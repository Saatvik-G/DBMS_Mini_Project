1. Problem Statement & Architecture Rationale

Modern criminal intelligence platforms handle two distinct categories of data: (1) highly structured, legally accountable operational data (such as chain-of-custody transfer records, case assignments, warrants, and suspect associations), and (2) polymorphic, semi-structured forensic data (including witness transcripts, CCTV telemetry, phone extraction dumps, and financial transaction streams).

Attempting to store all data within a single database paradigm leads to clear architectural compromises. A relational-only approach produces sparse tables with excessive null fields, schema migration friction, and difficulty storing nested telemetry. Conversely, a document-only approach lacks native ACID transactional guarantees, foreign key cascade enforcement, and kernel-level role-based privileges required for evidentiary integrity in court proceedings. We resolved this challenge by implementing a polyglot persistence architecture:

2. Architectural Trade-Off Analysis

Operating a polyglot persistence architecture introduces specific trade-offs that we addressed through explicit architectural decisions:

  • Eventual Consistency across Stores: Relational tables store authoritative foreign keys, while MongoDB documents store cross-store reference strings (case_id). We do not perform distributed 2-phase commits across PostgreSQL and MongoDB; instead, the application-layer API validates entity existence before persisting documents, providing high write availability.
  • Unified Search Latency: Rather than running sequential queries, FastAPI dispatches search requests to PostgreSQL and MongoDB in parallel using asyncio.gather, merging and ranking results before returning a single JSON response.
  • Database Engine Portability: To prevent evaluator lock-in, our database layer uses SQLAlchemy 2.0 with automated dialect detection. If a live PostgreSQL server is unreachable, the system automatically falls back to a local SQLite database with identical tables and constraints.
